# Role triggers and major review milestones

Read before selecting a delegate or setting a substantial project's review schedule. The coordinator applies these conditions through native tools. Role registration and descriptions are not a deterministic scheduler, token budget or automatic proof that dispatch worked.

## Select once at a decision boundary

Use a direct command/script for deterministic work. Keep tiny known lookups in the main thread. For model work, choose the least expensive available role that can reliably answer the bounded question under its tools and authority; small per-token price alone does not cover startup, context, validation and integration costs. Delegate when independence, substantial context reduction or independent challenge justifies those costs. The main agent can own any suitable task directly.

| Role | Entry trigger and evidence | Codex default | Claude default | Stop or transfer |
| --- | --- | --- | --- | --- |
| scientific_explorer | Substantial specified file/log/symbol extraction. Input paths/search question are known; independent retrieval saves owner work. | Luna/high; specified caller/test tracing within reader scope | Haiku/high; mechanical lookups only | Return requested facts with locations and unchecked areas, then stop. Interpretation goes to owner/analyst; no implementation. |
| scientific_researcher | A bounded primary-source question needs applicable versions/passages; source retrieval is a separate useful lane. | Luna/high | Sonnet/medium | Return evidence and unresolved source gaps. Scientific synthesis/method decisions go to owner/analyst. |
| scientific_worker | A well-specified substantial implementation/check lane has owned paths, acceptance checks and authorized resources. Delegate only when this improves context/parallel work. | Sol/medium | Sonnet/medium | Own the dependent change through its named checks/checkpoint. Return consequential ambiguity to the coordinator, without spawning another team. |
| scientific_analyst | A concrete demanding synthesis, derivation, statistical or numerical interpretation exceeds mechanical retrieval. Inputs and decision are specified. | Sol/high | Sonnet/high | Return supported analysis, alternatives and limits. Do not authorize new experiments or replace required independent review. |
| scientific_reviewer | Project scope/planning, a declared major phase decision, final project review, or one justified material exception. Original requirements, exact evidence and the decision are available. | Astra/high | Opus/high; no shell | Return disposition, consequential findings and next checks, then stop. No edits, tests, polling, new attempt or claim promotion. |

Easy mechanical transformations use scripts where possible. Reader roles do not acquire write tools just because a task is easy. A smaller-model writer is an optional native/ad hoc allocation only when explicitly scoped, tool-compatible and verifiable; never silently convert the explorer or transfer scientific method ownership. Preserve the user's explicit model choices and existing role definitions.

A harder question discovered by a helper is a handoff, not authority to broaden its search, change its tier or run experiments. The coordinator transfers the affected decision with the existing evidence rather than making both agents redo the same investigation. Routine debugging stays with the execution owner; escalate to analysis for a reasoning gap or review for a challenged consequential direction.

## Set the review schedule in the existing plan

Use the project's declared phases and gates; do not invent milestones for individual files, tasks, tests, retries or elapsed-time intervals.

| Review moment | Trigger | Packet and consequence |
| --- | --- | --- |
| Scope and plan | New substantial scientific objective or material scope/method/acceptance change before costly execution; no applicable reviewed plan exists | Objective, alternatives, controls, proposed observables, acceptance/resource/stop boundaries. Reuse a still-applicable reviewed plan. |
| Major phase gate | A named phase deliverable is complete and the plan requires an independent decision before the next consequential phase/allocation | Exact phase artifacts and required terminal checks; one review can cover several completed subtasks serving that same gate. |
| Final project review | The authorized substantial project/checkpoint deliverables and named checks are complete | Requirements-to-evidence coverage, negative results, limitations and unresolved items. Fresh context if the reviewer authored the plan. |
| Material exception | New evidence invalidates a central assumption, a consequential strategy repeatedly fails, claim authority changes, or the user/project requires a review | Narrow blocked decision plus evidence and explicit missing items. A blocking review cannot certify future readiness/completion. |

Register the review moment, blocked decision and entry evidence once in the current plan/contract. At an event, check whether the applicable disposition already covers the same inputs and decision. Reuse it when valid; changes invalidate only affected findings/checks, while preserving any project-required broader review. Missing gate evidence returns to the execution owner before readiness/completion dispatch. Do not reactivate the reviewer with an unchanged incomplete packet.

Final review of a small routine task is not automatically final project review. A required review cannot be skipped to reduce cost or to reach a preferred milestone. The selected reviewer is an independent role, not a permanent supervisor of every task.

## Waiting is not another role trigger

Job start, an unchanged progress poll and a user status question do not activate explorer, analyst or reviewer. The existing progress owner uses native notifications or bounded polling. Report the last verified state and its age when no new signal is available; do not imply fresh progress. Observe declared safety deadlines with deterministic tools. Completion activates the next authorized plan step; only a major gate/exception activates consequential review.

These are instruction-level triggers. Verify actual native dispatch when a model/routing change warrants it and evaluate cost/quality under a bounded matched-outcome test. Neither this table nor a static PASS guarantees zero wasted tokens or maximal efficiency.
