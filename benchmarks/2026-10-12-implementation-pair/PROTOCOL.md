# Fresh implementation comparison: preparation protocol

Status: offline preparation. No paid start authorized. This is a new synthetic
implementation task; it does not reopen any previous failed or stopped arm.

## Question and limits

On one small, dependent implementation task, does allowing bounded independent
retrieval change accepted quality, reported family cost or elapsed time compared
with one capable owner doing retrieval? Both arms retain the same consequential
review gate. This tests a routing option, not a model ranking or the benefit of
removing review. One synthetic pair cannot establish general savings, long-task
reliability, real compaction behavior or scientific success. If the support arm
chooses no explorer, it does not estimate a helper effect. A tiny retrieval lane
may rationally be done directly; do not force delegation to obtain an effect.

The fresh task repairs a batch-duration report across dependent Python modules.
Its documents specify units, missing and invalid values, attempt ordering and
report shape. The owner interprets, implements, integrates and checks. The
optional explorer may only retrieve exact named contract sections and locations;
its return must replace owner retrieval. It cannot interpret code or repair it.
This is closer to implementation than the earlier extraction fixtures, but it
remains a small synthetic workload, not a representative production sample.

## Matched controls and intervention

| Control | Both arms |
| --- | --- |
| Main | Claude native `opus`, high effort; observed identity recorded |
| Tools | Read, Glob, Grep, Bash, Skill, Agent, Edit, Write |
| Files | Identical initial source, public tests, contracts, skill and instructions |
| Review | Exactly one native scientific_reviewer after final edit and full public check |
| Reviewer | Existing native Opus/high definition, read-only; no tool or model changes |
| Budget | Proposed $1.50 CLI reported limit per family; 300 s deadline each |
| Cap | Two direct helpers maximum, no nested delegation, sequential families |
| Outcome | Same hidden oracle, full public check receipt and final-version review |

`owner` performs retrieval directly and calls only the mandatory reviewer.
`support` may call at most one native scientific_explorer (existing Haiku/high)
for the disclosed retrieval assignment, plus the same mandatory reviewer. Tool
availability stays equal; helper permission differs by intervention. Neither arm
uses workers, researchers, analysts or extra reviewers. No changes after review:
a finding that needs repair is a failed task outcome for this fixed trial.

Order is sampled once with the system random generator during preparation and
stored before any model output. There is no reverse pair or retry. Separate new
session IDs avoid shared conversation. Global catalogs/settings may remain
visible in both arms; input caching and backend variation cannot be controlled.
Record cached and uncached input separately and do not claim causal isolation
from a single sequential pair.

## Acceptance and capture

The named public check is supplied by the fixture. The owner saves its complete
stdout/stderr and verified exit in workspace `receipts/`, then records hashes of
all editable sources and the log in `receipts/review-input.json`. The reviewer
reads those exact files, original contracts and full check evidence. Preserve the
native review response and final source hashes. The final reply may be plain
text: no hidden quotation, whitespace or enum acceptance rules apply.

After termination, preserve command, prompt, source/input/config identities,
full CLI stdout/stderr, terminal exit/timeout, owned-process cleanup and owned
native parent/child transcripts. Use the existing native capture/accounting
utilities; unsupported evidence stays unknown. Run the fixture oracle against
the final workspace in a bounded local process. Check immutable-file hashes and
new files (only editable sources and `receipts/` may change). Public tests must
still be the frozen tests. Independently assess raw evidence for: exact reviewer
count/role/native linkage and completed response; final source/log hashes bound
to that review; actual full public-check completion; hidden oracle outcomes;
permission/helper boundaries; complete usage and terminal cleanup. A model's
claim of success or a written receipt alone cannot prove execution.

Keep implementation correctness, observed review behavior, literal output,
measurement validity and unknown evidence separate. Both successful and failed
implementations are outcomes. A valid implementation failure does not stop the
second arm. Missing capture/accounting, invalid permissions, unexpected helpers,
timeout or unverified cleanup stops the pair before another start. Unknown is
never pass. After arm one, independently verify these continuation conditions
and freeze that assessment before arm two. No automatic launch or retry.

## Accounting and proposed allocation

Proposed new allocation: exactly two parent starts, at most three child starts
(two mandatory reviewers and one optional explorer), sequential families,
$1.50 CLI reported limit each ($3.00 nominal total), 300 seconds each plus owned
cleanup. These limits may overshoot after a response; they are not hard dollar
ceilings. The proposal is not authorization and old unused allocation is not
available. The allocation file remains `approved: false` until the user approves
this exact scope and reported-limit interpretation.

Report each family's CLI aggregate once, including its owner, integration,
reviewer and optional explorer; preserve per-model usage to check inclusion and
avoid double counting. Same-model inclusion must be verified from the owned
parent and child transcripts: deduplicate assistant responses by stable message
ID within each owned thread, exclude child echoes from parent-stream totals, and
reconcile input, output, cache-read and cache-creation token sums per model with
the CLI terminal modelUsage counters. Missing IDs, conflicting final counters,
unsupported cumulative/partial usage or any unexplained mismatch leaves family
inclusion unknown and stops before arm two. Merely summing per-model dollar
estimates is not proof that the same-model reviewer was included. Retain the
per-response reconciliation table and raw terminal counters as evidence.
Record wall time, output and cached/uncached input for
both outcomes, including failures. Same-model parent/reviewer cost attribution
may be unavailable. Preparation, coordinator and external assessment cost are
separate and currently unmetered; total project cost stays unknown. If only one
arm is valid, publish the partial result without savings. If both are valid,
report quality first and observed family totals/difference descriptively, without
general or complete-cost savings claims.

## Named completion checks and boundary

Offline preparation must pass fixture reference and negative controls, matched
input/control and drift checks, explicit refusal of an unallocated start,
repository validation, full unit discovery and skill structure validation.
Preserve full logs/exit receipts and all historical benchmark hashes. Independent
plan/readiness review must assess workload relevance and controls as well as
code. Finish at a local Git checkpoint, with no push or changes to live skill,
native settings, agent definitions or paused scientific projects.

After preparation is independently accepted, request the new allocation. The
maintenance rule is: "Run fresh model-backed evaluation only when its scope and
cost are authorized." No model calls are part of offline preparation. The new `scripts/implementation_pair.py launch` entrypoint checks the frozen
pair, allocation and independent readiness record before invoking the existing
owned-group runner. It writes an exclusive start marker before launch; terminal
capture never self-certifies quality or accounting. Before arm two it requires
`continuation.json` with a named independent reviewer, the exact terminal hash,
and all named continuation checks true. These local records document authority
and review; they are not authentication or an OS security boundary. Do not use
old behavioral/native `run` entrypoints, which enforce different contracts.
